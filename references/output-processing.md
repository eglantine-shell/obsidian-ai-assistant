# Output Processing

产出是用户实际做过、完成过或 materially participated in 的成果。它们通常比“我喜欢什么”更能帮助 AI 理解用户的实践范围，但不同类型的产出能证明的事情不同。

## 1. 文本产出优先保留原文

对于文章、论文、小说、同人、报告、方案、教案、课程作业等文本型成果：

- 能取得正文时，优先保存全文或忠实 Markdown 转写；
- 不要用 AI 摘要替代原文；
- 只做必要的格式转换和档案信息补充；
- 用户自己的文字不要为了“整理得更好”被重写。

AI 可以另做 corpus synthesis，但 synthesis 和原始 output 必须是两层。

## 2. 大型项目保存 record，不必复制整个工程

软件、游戏、设计工程、摄影项目、视频项目、大型数据项目等，通常有更自然的 canonical location。

Obsidian 可以保存 output record，至少说明：

- 项目是什么；
- 时间；
- 当前状态；
- canonical location；
- 用户实际负责什么；
- 关键结果；
- 重要工具 / 协作方式；
- AI 是否实质参与。

不要为了“都放进 Vault”复制整个 Git 仓库、Figma 工程或大型二进制资产。

## 3. 普通人的 output 不一定是“作品”

以下都可能是有效 output evidence：

- 工作 PPT；
- Excel 模型；
- 教案；
- SOP / 流程文档；
- 研究报告；
- 项目复盘；
- 简历和作品集；
- 课程作业；
- 家庭预算表；
- 活动方案；
- 运营计划；
- 设计稿；
- 代码项目。

是否值得归档，取决于它能否帮助未来 AI 理解“这个人实际做过什么”，而不是它是否足够正式。

## 4. 项目级 AI-assisted 标签不够

“这个项目是 AI-assisted”只说明 AI 在项目中实质参与过，不能自动说明用户完成了项目里的哪些具体动作。

尤其不要从以下事实直接推导用户能力：

```text
仓库里存在某份文档
≠ 用户提出要写这份文档
≠ 用户撰写了这份文档
≠ 用户设计了这份文档的结构或约束
≠ 用户实质审阅并理解了这份文档
```

同样：

```text
项目由用户发起
≠ 项目内每个 artifact 都由用户设计
```

```text
用户最终接受了 AI 生成内容
≠ 用户具备独立生成同类内容的能力
```

如果未来 synthesis 要引用某个具体动作来证明能力，必须继续确认这个动作本身的 provenance。

## 5. 使用 contribution-level provenance

对 AI 协作项目，不需要把每个文件都做成复杂审计日志，但凡一个具体 artifact / action 可能被用于能力判断，就应尽量区分：

- **initiated**：是谁提出需要这个东西；
- **specified**：是谁定义要求、约束、内容标准或结构；
- **authored / generated**：主体内容是谁写或生成的；
- **edited**：谁做了实质修改；
- **reviewed**：谁实际检查并给出判断 / 反馈；
- **approved**：谁明确决定采用；
- **integrated / executed**：谁把它接入真实工作流并使用；
- **maintained**：后续谁持续维护；
- **unknown**：现有 evidence 无法确定。

这些动作不能互相替代。

例如：用户要求 AI 写一份测试计划，并逐条审阅、修改后采用，可以支持“用户定义测试要求、审阅和迭代测试计划”的实践证据，但仍不等于“用户独立撰写了测试计划”。

反过来，如果 AI 自己建议创建一份 AGENTS.md / 约束文档并自行生成，用户只是让项目继续运行，那么这份文档的存在不能证明用户具有“编写 AI 约束文档”的能力。

## 6. 能力 claim 必须回溯到具体贡献证据

在从 output 形成能力判断前，执行一次反向检查：

> 我准备说“用户会 / 做过 X”，当前 evidence 是否真的证明 **X 是用户完成的动作**？

可用 evidence 包括：

- 用户明确自述；
- 对话中用户实际提出的要求；
- 用户写下的原文；
- Git / revision history 能区分的实质修改；
- review / feedback 记录；
- 明确的任务分工或项目说明；
- 其他能够直接支持具体贡献的记录。

如果只能证明“这个 artifact 存在于用户项目里”，就把贡献标记为 unknown，不要补猜。

## 7. AI-assisted output 可以证明什么

只有在对应贡献有独立 evidence 时，AI-assisted 项目才**可能支持**这些实践判断：

- 用户定义过需求；
- 用户提出过约束或验收标准；
- 用户做过测试和迭代；
- 用户做过选择、审稿、整合或方向控制；
- 用户实际使用 AI 工具完成并交付过某类任务；
- 用户持续维护过某项规则或工作流。

不要因为这些动作“通常由项目 owner 完成”就默认归给用户。

## 8. 团队产出也要保留贡献边界

如果一个成果由多人完成，尽量保存用户的实际角色：

- 主笔；
- 共同制作；
- 编辑 / 审核；
- 项目管理；
- 视觉设计；
- 数据分析；
- 仅参与其中一个模块。

不清楚时，通过 interview protocol 询问，而不是默认整项成果都由用户完成。

AI 也应当被视为一种协作者来源：不要因为它不是人类团队成员，就降低 provenance 要求。

## 9. 结果和能力不要自动画等号

销售、获奖、发布、播放量、通过审核、上线等 outcome 可以作为重要 evidence，但结果本身不能解释原因。

一个项目成功，不足以单独证明广泛的专业能力；一个项目失败，也不能单独证明缺乏能力。

## 10. 产出如何进入 corpus

单个 output 先作为 evidence。

当同类产出积累到足以形成稳定理解时，再做 corpus synthesis，例如：

- 写作实践；
- 设计实践；
- 学术工作；
- 软件项目；
- 教学成果；
- 职业项目。

综合层应基于整个 corpus，而且每个能力结论都要服从底层 contribution provenance，不能因为项目整体属于用户就把内部所有 artifact 的设计、写作和决策都归给用户。

## 11. Output record 示例

```markdown
# 项目名称

- 时间：2026
- 状态：已完成
- 原始位置：<path or URL>
- 类型：软件项目
- 协作：AI-assisted

## 已确认的用户贡献

- 产品需求：用户提出并持续迭代
- 测试：用户执行并反馈
- 视觉判断：用户确认

## 其他项目 artifact

- 实现代码：主要由 AI 生成
- 项目约束文档：AI 生成；是否由用户提出 / 实质维护未知

## 结果

已发布可用版本。

## 能力边界

本项目支持产品定义、测试和 AI 协作实践；不直接支持独立编码能力，也不在 provenance 未确认时支持“编写项目约束文档”等更细的能力 claim。
```

字段和目录应服从用户现有 Vault，而不是强制使用这个模板。
